## 2. 実装した PoC の構成

```
[Explorer で Space]
   │ WH_KEYBOARD_LL（専用スレッド）: SpaceKeyClassifier（既存・無変更）+ TypingTracker（IME/タイプアヘッド）
   │   → 対象なら Space を握りつぶし、キューに投入（フック内では COM を呼ばない）
   ▼
[選択取得] 専用 STA スレッド: IShellWindows → IShellBrowser → IShellView → IFolderView2::GetSelection
   ▼
[表示] UI スレッド: 事前生成済みウィンドウを "panel" 方式で表示（§4）
   ▼
[段階表示] ①ファイル情報 → ②Windows サムネイルキャッシュ（専用 STA、INCACHEONLY）→ ③フル品質（WinRT BitmapDecoder、画面サイズへ縮小デコード / PDF は Windows.Data.Pdf）→ ④差し替え
[閉じる] Esc / Space（フック経由）、他アプリへの切替で自動クローズ（EVENT_SYSTEM_FOREGROUND）
[計測] QuickViewTimeline: QPC タイムスタンプを ETW（EventSource "Mavue-QuickView"）と JSON Lines に出力
```

## 3. 実測で判明した Windows の挙動

### 3.1 Shell COM はスレッドアパートメントに依存する（実測）

| 呼び出し元 | `IShellBrowser::GetWindow`（Explorer への越境 COM） |
|---|---|
| MTA スレッド | **失敗** `0x8001010D` RPC_E_CANTCALLOUT_ININPUTSYNCCALL |
| STA スレッド | 成功 |

→ 選択取得は専用 STA スレッドで行う。`ExplorerSelectionProvider` は STA 以外では例外を投げる（誤用の早期検出）。

- Windows 11 のタブ: 各タブが `ShellTabWindowClass` と独自の `SHELLDLL_DefView` を持つ（実測）。フォーカス中アイテムビューの親 DefView と `IShellView::GetWindow` を照合して、アクティブタブを正確に特定できる。
- Explorer のファイル一覧のフォーカスクラスは `DirectUIHWND`、親は `SHELLDLL_DefView`（25H2 で実測）。既存の判定ロジックの前提どおり。
- シェルサムネイル（`IShellItemImageFactory`, `SIIGBF_INCACHEONLY`）は MTA/STA どちらでも動作。**プロセス内初回のみ約 60 ms、以降 4〜7 ms**（実測）→ 起動時にプリウォームする。キャッシュに入っていたのは 256px（Explorer の表示サイズ依存）。

### 3.2 前面表示（最重要）

#### 比較した方式

| 方式 | 内容 |
|---|---|
| `setforeground` | `AppWindow.Show(true)` + `SetForegroundWindow` |
| `appwindow` | `AppWindow.Show(true)` のみ |
| `hookgrant` | フックのコールバック内（入力処理中）で `AllowSetForegroundWindow(自プロセス)` → `SetForegroundWindow` |
| `attach` | `AttachThreadInput` で前面スレッドと入力キューを結合して `SetForegroundWindow`（比較用ハック） |
| `noactivate` | `SetWindowPos(HWND_TOP, SWP_NOACTIVATE)`。前面化しない |
| `noactivate-topmost` | 一瞬だけ `HWND_TOPMOST` にしてすぐ解除（比較用） |
| **`panel`（採用）** | `SetWindowPos(HWND_TOPMOST, SWP_NOACTIVATE)`。**表示中だけ最前面帯**、前面化しない、他アプリへ切替で自動的に閉じ、閉じる前に Topmost を解除 |

`AllowSetForegroundWindow` を「Explorer 側から呼んでもらう」方式は、Explorer 内でコードを実行する手段がないため Space 経路では適用不可（コンテキストメニュー経由なら、Explorer 内で動く `IExplorerCommand` が呼べるので有効。§6）。

#### 結果（実測）

**(a) ユーザーの実操作（最も信頼できるデータ）**

| 入力 | 方式 | 結果 |
|---|---|---|
| 物理キーボード（`injected:false`、11 回） | `auto`（hookgrant + 失敗時は非アクティブ表示） | フック内の権利確保は **2/11 回しか成功せず**（成功した 2 回は、ユーザーがタスクバーから Mavue を前面にした直後）。失敗時はタスクバーが点滅し、非アクティブのまま表示 → ユーザー評価「問題あり」 |
| リモート操作（Parsec 経由、`injected:true`） | `noactivate` | **Space 直後から Explorer の後ろに表示** → ユーザー評価「問題あり」 |
| リモート操作（同上、15 回の操作） | **`panel`** | 表示 8/8 回すべて Explorer の上（`aboveOwner=True`）。Space→Space、Esc、Alt+Tab による自動クローズもすべて期待どおり → ユーザー評価「**問題なし**」 |

**(b) 自動ハーネス（SendInput による注入入力）**

- ハーネスがホストを**自分の子プロセスとして起動**した場合や、ハーネスを Bash から起動した場合は、`setforeground` 以外のほぼ全方式が成功した（例: `hookgrant` 19/19、`noactivate` 25/27）。
- しかし、**ホストを独立に起動し、ハーネスは接続するだけ**の条件で、ユーザー報告と同じ失敗が再現した: `noactivate` **0/12 で Explorer の後ろ**、同条件の `panel` は **12/12 で上に表示**。
- 同じ条件の再試行では `noactivate` も成功した（6/6）。→ **前面化や z 順の結果は、入力元（物理・リモート・注入）、プロセスの起動元や履歴、リモート操作ツールの有無など、ハーネスでは制御しきれないシステム状態に左右される**（実測）。具体的に何が決め手かは特定できていない（推測の域）。
- 自動で前面を取るアプリ（本環境ではターミナルの Warp）が計測中に前面化し、数件の計測が乱れた（実ユーザー入力は 0 件と記録）。ハーネスは「キー送信直前に前面ウィンドウを確認し、違えば送らない」ガードでこれを検出した。

**結論**: 自動テストで成功しても、実環境で成功するとは限らない。前面化の権利（`SetForegroundWindow` / `AllowSetForegroundWindow`）にも、権利がないと効かない z 順の引き上げ（`HWND_TOP`）にも依存しない方式が必要。**Topmost 帯への配置は権利不要の正規の仕組み**であり、実ユーザー入力で唯一安定した `panel` 方式を採用する。

#### `panel` 方式の UX 仕様（採用）

| 操作 | 挙動 | 検証 |
|---|---|---|
| Explorer で Space | プレビューが Explorer の上に浮かぶ。**Explorer がキーボードフォーカスを保持**（矢印キーなどは Explorer に届く） | ユーザー実操作 + ハーネス 27/27 |
| Esc | フック経由で閉じる（Explorer が前面で、Quick View が非アクティブ表示中の場合のみ Esc を横取り） | ユーザー実操作 + ハーネス |
| Space（表示中） | 同じファイルなら閉じる（トグル） | ユーザー実操作 6 回 + シナリオ |
| Explorer をクリック | プレビューは開いたまま（Explorer は持ち主） | シナリオ |
| プレビューをクリック | 通常のアクティブウィンドウになり、以降のキーはプレビューが受ける | 実装済み・**ユーザー未確認** |
| 他アプリへ切替 / Alt+Tab | プレビューは自動で閉じ、Topmost も解除。他アプリの上に残らない | ユーザー実操作 2 回 + シナリオ |
| タスクバーの点滅 | 前面化を試みないので発生しない | ユーザー評価「問題なし」 |

「強制 Topmost は避ける」という要件との関係: `panel` の Topmost は (1) フォーカスを奪わない、(2) Quick View が表示されている間だけ、(3) 持ち主の Explorer 以外が前面になった瞬間に閉じる、という範囲に限定しており、ユーザー操作を奪わない。macOS の Quick Look パネル（Finder の上に浮くパネル）と同等の振る舞いである。**この判断はユーザーの最終承認事項**として報告する。

| JPEG 800×600 | 5.0 ms | 10.1 | 13.6 | （先にフル品質） | **20.7** | 51.9 | 3.2 | 146 MB |
| JPEG 6000×4000（24 MP） | 3.8 | 8.3 | 12.2 | 20.9 | 103.2 | 54.8 | 79.4 | 205 MB |
| PNG 4000×3000 | 5.1 | 11.8 | 16.8 | 27.8 | 152.0 | 70.7 | 132.4 | 271 MB |
| WebP 1600×1200 | 4.1 | 9.0 | 12.4 | 23.0 | 72.1 | 55.8 | 44.9 | 278 MB |
| AVIF 1600×1200 | 3.7 | 8.0 | 11.3 | 28.9 | 61.5 | 54.0 | 37.5 | 278 MB |
| HEIF 4000×3000 | 3.4 | 7.4 | 11.1 | 17.5 | 337.4 | 52.0 | 322.9 | 460 MB |
| PDF（1 ページ, Windows.Data.Pdf） | 3.6 | 7.8 | 10.7 | –（キャッシュなし） | 33.5 | 62.2 | 13.7 | 530 MB |

- フック内の処理は 0.0〜0.6 ms（QPC 差）。
- 「画面上で画素を検出」はハーネスが `GetPixel` で画面をポーリングした値で、DWM の合成と `GetPixel` 自体のコスト（数十 ms 単位）を含む粗い上限値。アプリ内の「最初のフレーム」「サムネイル表示」「フル品質表示」は `CompositionTarget.Rendering` 時点。
- **白画面で待つことはない**: 大きな画像でも Space 後 11〜17 ms でウィンドウが描画され、17〜29 ms でキャッシュ済みサムネイルが表示され、その後フル品質に差し替わる（実測）。
- ピーク WS はプロセス生存中の最大値なので、表では後の行ほど前のケースを含む。単独計測は §3.5。

### 3.4 デコード方式の比較（実測、フル品質表示までの中央値）

| 画像 | WinRT Fant（既定） | WinRT Linear | WinRT Nearest | WinRT Cubic | XAML DecodePixelWidth |
|---|---|---|---|---|---|
| JPEG 24 MP | 110 ms | 83 | 91 | 244 | **78** |
| HEIF 12 MP | 345 | 334 | **274** | 415 | 547 |
| JPEG 192 MP | 454 | 318 | 321 | 442 | **240** |
| PNG 100 MP | 765 | **703** | 702 | 784 | 779 |

- WinRT 経路では、JPEG の DCT 段階縮小（`IWICBitmapSourceTransform`）が効いていないと**推測**される（192 MP で 240 ms 以上かかる）。WIC を直接使う経路（ソース変換で 1/2〜1/8 にデコード → Fant で仕上げ）は次の検証課題。
- PoC の既定は画質優先で Fant のまま（サムネイル → フル品質の段階表示で体感速度を確保）。

## 5. 設計への反映

| 変更前 | 変更後 | 理由（実測） |
|---|---|---|
| Space で Quick View を**アクティブ化**して前面に出す | **`panel`**: 非アクティブのまま表示中だけ最前面帯に浮かべる。Explorer がキーボードを保持し、Esc/Space はフックで処理 | 前面化の権利は実ユーザー入力では得られない（物理キーで 9/11 失敗）。`HWND_TOP` も権利がないと Explorer の上に出られない（リモート操作で後ろに表示） |
| 選択取得を MTA ワーカーで実行 | 専用 STA スレッド | MTA では `RPC_E_CANTCALLOUT_ININPUTSYNCCALL` |
| サムネイル取得をスレッドプールで実行 | 専用 STA スレッド + 起動時プリウォーム | 初回 60 ms のシェル初期化を Space の経路から除外 |
| 常駐ホストの出力名 `Mavue.QuickView.exe` | `Mavue.QuickView.Host.exe` | ライブラリ `Mavue.QuickView.dll` と同じフォルダでファイル名が衝突 |
| E2E でホストをハーネスの子プロセスとして起動 | WMI 経由で独立に起動（`--child-host` で旧挙動） | 子プロセス起動は前面化の結果を有利に歪める |

## 7. Explorer の選択変更への追従（第 2 工程で実装）

### 7.1 仕組み（ポーリングなし）

| 事象 | 受け取り方 |
|---|---|
| 選択・フォーカスの変化 | ビューの自動化オブジェクト（`IShellView::GetItemObject(SVGIO_BACKGROUND, IID_IDispatch)` = ShellFolderView）の **`DShellFolderViewEvents.SelectionChanged`（DISPID 200）** を接続ポイントで購読 |
| フォルダ移動 | ブラウザの **`DWebBrowserEvents2.NavigateComplete2`（252）** → 新しいビューへ購読し直す |
| ウィンドウ・タブを閉じた | `DWebBrowserEvents2.OnQuit`（253）→ Quick View を閉じる |

- 購読は Quick View 表示中だけ（Space 押下時に開始、閉じた時に解除）。イベントは Explorer からの越境 COM 呼び出しとして届くため、
  受信スレッドは**メッセージループ付きの専用 STA**（`MsgWaitForMultipleObjectsEx`）にした。待機中に Explorer を待たせない。
- 連続イベント（矢印キーの押しっぱなし等）は 1 回の読み取りにまとめる（コアレス）。読み取りは表示順（`IFolderView2::Items(SVGIO_SELECTION | SVGIO_FLAG_VIEWORDER)`）とフォーカス項目。
- 実測（Explorer がイベントを発行してから Mavue が表示を切り替え始めるまで）: **約 2 ms**（物理キーの実操作で中央値 1.9 ms、最大 5.8 ms）。
  キー押下から Explorer がイベントを出すまでは通常 15〜20 ms、大きいファイルへの移動で約 250 ms かかる場合があった（**Explorer 側の処理時間**、Mavue からは制御不可）。

### 7.2 単一選択・複数選択の挙動（`PreviewNavigator`、単体テスト 17 件）

| 状況 | 挙動 |
|---|---|
| 1 件選択で Space | **単一モード**。矢印キーは Explorer に任せ（表示形式ごとの並び・グループを Explorer が解釈）、Explorer の選択変更に追従 |
| 2 件以上選択で Space | **複数モード**。フォーカス項目（選択内なら）から表示。**←/→ は Mavue がフックで横取りし、選択内だけを移動**（Explorer の複数選択を壊さない）。端で止まる（循環しない）。情報欄に「2 / 3」 |
| 複数モードで ↑/↓ | Explorer に渡す → 通常は 1 件選択に変わる → 単一モードへ移行して追従 |
| Shift+矢印で選択を広げた | 複数モードへ移行 |
| Ctrl+矢印（フォーカスのみ移動） | 選択内でフォーカスが動いたら追従。同じ内容の再通知では、←/→ で移動した位置を保つ |
| 選択が空になった | Quick View を閉じる |
| Quick View をクリックしてアクティブにした | 矢印キーは Quick View に届く。複数モードは選択内を移動、単一モードは **Explorer の選択を前後に動かす**（`IFolderView::SelectItem`）→ その変化に追従 |
| 表示中に Space | 閉じる（どの項目を表示していても） |

- 横取りは「Quick View が非アクティブ表示中・複数モード・前面が持ち主の Explorer・フォーカスがファイル一覧・修飾キーなし」の全条件を満たす ←/→ だけ。

## 8. QuickLook との共存（第 2 工程）

### 8.1 原因（実測）

| 起動順 | 結果（注入 Space、各 3 回） |
|---|---|
| QuickLook → Mavue | Mavue のみ表示（3/3）。Mavue のフックが先に呼ばれて Space を消費するため QuickLook に届かない |
| Mavue → QuickLook | **二重表示**（3/3）。QuickLook のフックが先に呼ばれ、**Space を消費せずに流す**ため両方が反応 |

Windows は**後から設置された低レベルフックを先に呼ぶ**ため、起動順で結果が変わる。

### 8.2 対策（`HookMaintenance`）

- 既定（`--other-quicklook prefer`）: 10 秒ごとに既知ツール（QuickLook, Seer）のプロセス開始時刻を確認し、Mavue のフック設置より後に起動していたら
  **フックを再設置して先頭を取り戻す**（新フックを設置してから旧フックを外すので取りこぼしなし）。60 秒ごとの再設置はフックの無通知解除（タイムアウト）からの復旧も兼ねる（前回課題 P6）。
- `--other-quicklook yield`: 他ツールの動作中は Mavue は Space に反応しない（実測で確認）。
- 実測: QuickLook を Mavue の後に起動 → 約 6〜10 秒後に再設置 → 以後の Space は Mavue のみ（自動 9/9、物理キーでもユーザー評価「問題なし」）。
- **制限**: QuickLook 起動直後〜次の確認（最大 10 秒）の間は二重表示になりうる（実測 1/1）。起動イベントを即時に受け取る方法（管理者不要のもの）は未調査。
- 確認はプロセス一覧の読み取り（数 ms 未満）で、Explorer の選択監視とは無関係。

## 10. 第 3 工程: タブ追従・先読み・高速デコード・表示サイズ

### 10.1 Explorer のタブ切替への追従

- 仕組み: `SetWinEventHook(EVENT_OBJECT_FOCUS)` を**持ち主の Explorer プロセスに限定**して受け取り、フォーカスが同じウィンドウ内の別のファイル一覧（`SHELLDLL_DefView` 配下の `DirectUIHWND`/`SysListView32`）に移ったときだけ、そのタブの選択を読み直して監視先を付け替える（`ShellViewFocus.IsOtherItemView`、単体テスト 6 件）。ポーリングなし。
- 実測（E2E `tab-switch-follow`、Ctrl+Tab）: タブ 2 の画像を表示するまで 196〜217 ms、タブ 1 に戻るまで 79〜106 ms。物理キーでもユーザー確認済み（②）。
- 内訳の推測: 大半は Explorer がタブを切り替えて新しいビューを用意する時間（Mavue 側はイベント受信 → 表示開始が約 2 ms）。

### 10.2 前後の先読み

- 表示中の項目の前後（単一選択ではフォルダー内の前後、複数選択では選択内の前後）を、表示後にバックグラウンドでデコードしておく。キャッシュは LRU で 192 MB まで（`PreviewCache`、単体テスト 12 件）。64 MB を超えるファイル・4,000 万画素を超える画像（原寸表示時は 1,600 万画素）は先読みしない。
- 実測: ↓ で次のファイルへ移ったときのフル品質表示 103.6 → **30.5 ms**、複数選択内の → 116 → **10.3 ms**。人の操作速度（300 ms 間隔）での ↓ は 30〜39 ms、→ は 12〜16 ms。
- 先読みが巨大画像まで対象にしていた段階ではピーク WS が 807 MB になったため、上記の上限を設けた（同条件で 675 MB → 現在 462 MB。§10.5）。

### 10.3 JPEG の WIC 直接デコード

- JPEG は WinRT `BitmapDecoder` を通さず WIC を直接使う（デコーダー → Fant スケーラー → EXIF 回転 → BGRA）。WIC のスケーラーが JPEG の DCT 段階縮小を内部で使うため速い。
- 実測（フル品質表示）: 192 MP JPEG 449 → **251 ms**、24 MP JPEG 108 → **87 ms**。PNG は差がないため従来経路のまま（約 133〜150 ms）。
- EXIF 回転 1〜8 はすべて Windows 自身のデコーダーと画素単位で一致することを単体テストで確認（Mavue.Image.Tests）。
- 色管理: この経路は色変換をしないので、ICC プロファイル付き・sRGB 以外の EXIF 色空間の画像は従来の色管理付き経路に回す。WIC でエラーになった場合も従来経路で再試行する。
- デコード結果は `SoftwareBitmap` のメモリへ直接書き込む（中間の配列を作らない）。§10.5 の原寸表示時のメモリ増加の対策。

### 10.8 拡大率の異なる複数モニター・表示中のリサイズ

- 不具合（実測、3 モニター: 4K 150 %・1920×1080 100 %・2560×1080 100 %）: 別のモニターにある Explorer から開くと、拡大しないモードの画像が 630×420 や 1035×690 など、ウィンドウより小さく作られることがあった。
- 原因: ウィンドウを移動先のモニターに合わせて配置した後、Windows が DPI の変更（`WM_DPICHANGED`）でウィンドウの大きさを変えていた。画像領域は XAML の最後のレイアウトから求めていたため、移動前の古い大きさでデコードしていた。
- 対策:
  - 配置後の大きさが要求と違えば、もう一度 `MoveAndResize` する（移動先のモニターでは要求どおりになる）。
  - 画像領域は XAML のレイアウトを使わず、`AppWindow.ClientSize` と `GetDpiForWindow` と余白・情報バーの DIP 寸法から計算する。
  - 表示中にウィンドウの大きさ・モニターの拡大率が変わったら（`SizeChanged` / `XamlRoot.Changed`、150 ms まとめ）、領域が 2 px を超えて変わった場合だけ表示中の項目を作り直す。作り直しの間は今の画像を残す（同じ項目なので紛らわしくない）。

| シナリオ | 結果 |
|---|---|
| `monitor-open-each`（Explorer を各モニターへ移して開く） | 4K 150 %: 配置 2688×1575・領域 2630×1397・デコード 2096×1397 / 1920×1080: 1344×810・1304×690・1035×690 / 2560×1080: 1792×810・1752×690・1035×690。いずれも DPI 一致、計算した領域 = XAML のレイアウト |
| `monitor-move-while-shown`（表示中に別モニターへ） | 4K → 1920×1080: 領域 1752×930 で作り直し（DPI 144 → 96）/ → 2560×1080: 同じ DPI・同じ大きさのため作り直しなし（正しい）/ → 4K: 2630×1397 で作り直し |

**PDF が 1.5 倍の大きさで作られていた（このとき見つけて修正）**

- 実測: A4 の PDF（793×1122 DIP）が、拡大しないモードで画像領域の高さ 1397 px に対して 1481×2096、100 % のモニター（領域の高さ 690 px）でも 731×1035 で作られていた。表示はスクロールなしのため、**ページの下側が切れていた**と考えられる（画面での確認はしていない）。原寸モードも 1785×2526（正しくは 1190×1683）。
- 原因（実測）: `Windows.Data.Pdf` の `RenderToStreamAsync` は、`DestinationWidth/Height` に**システムの DPI 倍率**（この PC では主モニターの 150 %）を掛けた画素数を出力する。ウィンドウが 100 % のモニターにあっても 1.5 倍だった。
- 対策: 出力倍率をシステム DPI で見積もり、指定サイズをその倍率で割って渡す。出力が予定と 2 px を超えてずれたら、実際の倍率を覚えてもう一度描画する（プロセス中 1 回だけ）。
- 修正後（E2E `monitor-open-each` に PDF を追加して確認）: 拡大しないモード 150 %: 987×1397、100 %: 486×690（どちらも領域の高さちょうど）。原寸モード 150 %: 1190×1683、100 %: 792×1122（100 %）。

### 11.2 IPC（名前付きパイプ）

- 名前: `Mavue.QuickView.<セッション ID>.<ユーザー SID の SHA-256 先頭 8 バイト>`（SID はそのまま出さない）。
- DACL: 現在のユーザーのみ許可、NETWORK（リモートログオン）は拒否。クライアントは `PipeOptions.CurrentUserOnly` で、パイプの所有者が自分であることを確認する（他ユーザーによるなりすまし対策）。
- 形式: 4 バイト長 + UTF-8 JSON（`Mavue.Core.Ipc`、ソース生成 System.Text.Json）。1 MiB を超える長さは確保前に拒否。バージョン・パス（完全修飾・NUL なし・長さ・件数）を検証。パスはログに残さない。
- 単体・結合テスト: 枠組み 16 件（`IpcFramingTests`）、パイプ 6 件（同時 20 クライアント、不正な長さの後も動き続ける、無効な依頼はハンドラーを呼ばない など）。

## 12. PDF のページ送り（2026-10-02）

- 以前は先頭ページだけを描画していた（試作の範囲。`GetPage(0)` 固定）。現在ページを `PdfPageCursor` で持ち、指定ページを描画する（キャッシュのキーにページを含める）。
- 操作: PageUp/PageDown（パネル表示中はキーボードフックが受け取り Explorer には渡さない。Quick View がアクティブなときはウィンドウ）、マウスホイール（1 ノッチ 1 ページ。原寸表示でスクロールできるときは、上下端でだけページを送る）、情報バー右の前後ボタン（複数ページの PDF のときだけ表示、端では無効）。先頭/末尾の先へは移動しない。
- ↑↓←→ は従来どおりファイル移動。別のファイルに移ると、戻ってきた PDF は 1 ページ目から。ウィンドウのリサイズ・モニター移動ではページを保つ。2 ページ目以降はシェルのサムネイル（1 ページ目）を出さない。
- 表示中のページの前後を先読みするため、ページ送りは 9〜22 ms（E2E 実測、Release）。

## 13. GIF アニメーション（2026-10-02）

- 以前は 1 コマ目だけを表示していた。現在は、1 コマ目を従来どおり表示した直後に、複数フレームの GIF なら再生に切り替える（`GifPlayer`）。
- フレームは Windows の GIF デコーダー（WinRT）で 1 枚ずつ復号し、`GifComposer` で論理画面（キャンバス）に合成する（フレームのオフセット・透過・破棄方法 0〜3）。
  保持するのはキャンバスと、破棄方法 3 のときの保存用コピーだけなので、フレーム数が多くてもメモリは増えない。
- 復号・合成はスレッドプールで、表示中のフレームの待ち時間のあいだに行う。UI スレッドはキャンバスを画像にコピーするだけで、待ちは非同期。
  遅延 20 ms 未満は 100 ms（ブラウザーと同じ）。ループ回数は NETSCAPE2.0 ブロックに従い、ブロックがなければ 1 回だけ再生して最後のフレームで止まる。
- 800 万画素を超える GIF は、毎フレームのコピーが UI スレッドの負担になるため 1 コマ目の静止表示のまま。
- ファイルの切替、ウィンドウのリサイズ（作り直し）、非表示で必ず停止し、ファイルを閉じる。再生は常に 1 つだけ。
- 実測（E2E、Release）: 100 ms 指定で中央値 109〜110 ms（標準タイマーの 15.6 ms 刻みによる）。

## 14. 動画・音声（2026-10-02）

- 形式はファイル先頭のシグネチャで判定し（`FileFormatDetector`。ISO BMFF のブランド、EBML の DocType、RIFF、ASF、Ogg、MPEG、ID3 など）、決められない場合は拡張子。
- 再生は Windows 標準の `MediaPlayer` + `MediaPlayerElement`（Media Foundation）。ファイルは `StorageFile` から渡し、プレーヤーが必要な分だけ読む（Quick View はファイルを読み込まない）。
  10 分・106 MB の WAV の再生中もホストのプライベートメモリは約 170 MB で横ばい（初回表示時の増加はウィンドウとメディア基盤の初期化分。閉じると減り、再度開いても増えない）。
- 映像は画像と同じく拡大しない（モニターの拡大率を考慮）。音声は音符アイコンと再生状態（再生中/一時停止/再生終了）、下部に標準の操作バー。
- 操作: 標準の操作バー（再生/一時停止・シークバー・音量/ミュート・キャスト）。キーボードは Quick View にフォーカスがあるとき（クリック後）だけ:
  Enter＝再生/一時停止、Ctrl+←/→＝10 秒シーク、Ctrl+↑/↓＝音量 10%。矢印・Space・Esc・PageUp/PageDown は従来どおり（操作バーにフォーカスが残らないよう、ウィンドウに戻す）。
  Explorer が前面のとき（パネル表示）はキーボードフックが従来のキーだけを扱うため、メディア操作はマウスで行う。
- ファイルの切替・非表示・終了・再生失敗で、必ず停止してプレーヤーとソースを破棄する。同時に存在するプレーヤーは 1 つ。古いプレーヤーのイベントは無視する。
- 壊れたファイル・デコーダーのない形式は「再生できません」と表示し、常駐プロセスは継続する（E2E で確認）。クラウドのみのファイルはダウンロードを避けて再生しない。
- 隣接ファイルの先読みは画像・PDF のみ（メディアは対象外）。
- 計測: 動画を開いてから再生開始（MediaOpened）まで約 150〜175 ms（30 秒・640×480 の MP4、E2E）。

## 15. 共通ビューアへの移行と E2E の不安定な失敗の調査（2026-10-02）

- 表示面（画像・動画/音声・メッセージ）、画像デコード、PDF 描画、GIF 再生、動画/音声のセッションを `Mavue.Viewer` に移し、本体（Mavue.App）と共有した（ARCHITECTURE §3.2）。
  Quick View 固有の制御（段階表示・先読み・計測・フック）は変えていない。計測ログの項目名・内容は同じ。
- 移行で見つけた不具合: 動画の再生中は画像用の領域が非表示になるため、その大きさ（0）で動画の上限を計算していた（本体で映像が 1 px になった。
  Quick View はウィンドウの大きさから計算するため影響なし）。表示面そのものの大きさを使うよう修正。表示面のサイズ変更通知も同じ理由で表示面から出す
  （以前は動画の再生中にリサイズしても上限が更新されなかった）。
- `media-video` の失敗（前回 13 回中 1 回）:
  1. 再現した 1 件（Enter の一時停止が「されていない」と判定）は**ハーネスの不具合**。ホストのログでは Enter を受け取り一時停止していたが、
     ハーネスのログ読み取りが追記途中の行を読み飛ばしていた。修正後は `media-video` 3 回・`media-esc-repeat` 40 回で失敗なし（修正前を含めて `media-esc-repeat` は 160 回中 0 回）。
  2. 前回の失敗（Quick View 上の Esc で閉じない）は再現せず。ログでは Esc の 0.5 秒前に「他のアプリが前面になった」ことで Quick View が閉じていた
     （前面はすぐ Explorer に戻っている＝一時的なウィンドウ）。当時はどのウィンドウかを記録していなかったため、閉じた理由に前面になったウィンドウのクラス・プロセス名を
     記録するようにした（`foreground-other`）。候補: Explorer・タスクバー・通知などの一時的なウィンドウ（`TransientForegroundClasses` に含まれないもの）。
- `cli-quickview` の失敗（今回、全体と同じ順序での実行で 4 回中 4 回）: Windows が `SetForegroundWindow` を拒否し（前面化の権利が与えられない）、表示はパネル表示に切り替わった（設計どおり）。
  その直後に遅れてウィンドウが前面になると「ユーザーがクリックした」扱い（通常のウィンドウ）になり、Explorer に戻ってからの Esc で閉じない。
  変更前（HEAD）のホスト・変更前の Mavue.exe でも同じ順序で同じく失敗し、「他のアプリ」（Mavue.exe）を起動しない `--warm` では成功、単独実行でも成功するため、
  今回の変更ではなく実行環境（前面化の権利）に依存する。遅れて前面になる場合の扱いは課題 15。
